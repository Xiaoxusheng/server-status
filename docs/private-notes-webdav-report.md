# 私人手记图片 WebDAV 上云（OpenList → 移动云盘）可行性报告

> 评估日期：2026-09-10
> 结论先说：**可行，但不建议做「文件系统级挂载」（rclone mount / davfs2 直接当 storage_dir）；建议做「应用层 WebDAV 异步双写」**。
> 另外一个重要事实：**图片目前已经有云端副本** —— 现有的 `pv-backup.sh` 每日定时把 `private_notes.db + data/notes`（含全部加密图片）打包 AES-256-CBC 加密后上传到 OpenList 挂载的移动云盘。如果诉求只是"图片不丢"，现有链路已经实现，下面方案解决的是"实时性"和"省服务器磁盘"两个更强的诉求。

---

## 一、现状梳理（代码事实）

图片管线的完整链路（`private_notes_crud.go` / `private_store.go` / `private_api.go`）：

| 环节 | 现状 |
|---|---|
| 上传 | `POST /api/private/notes/{id}/images`，≤20MB，magic 嗅探校验 |
| 存储 | AES-GCM 加密落盘（`PVMEDIA1` 头，密钥 = sha256(SERVER_STATUS_ENCRYPT_KEY)），路径 `data/notes/YYYY/MM/DD/f_xxx.ext`，SQLite `note_images` 表记相对路径 |
| 缩略图 | 上传时同步生成 480px JPEG q82（`.thumb.jpg` 同目录），DB 持久化 thumb_path 与宽高；历史图片首次访问按需生成（singleflight 去重） |
| 读取 | `…/images/{iid}/file` 与 `/thumb`，双层认证 + 归属校验，`os.ReadFile` → 内存解密 → `http.ServeContent`，immutable 长缓存 + ETag（os.Stat ModTime） |
| 其他媒体 | 语音（整块加密）、卡片 PNG（`cards/` 目录）、手记视频（`PVVIDEO1` 分块加密，**依赖 ReadAt 随机读支持 Range 播放**）、全量导出 zip |
| 启动 | `migratePlainMedia` 遍历 storageDir，把历史明文原位迁移为加密 |
| 云链路 | `deploy/pv-backup.sh` + `/etc/cron.d/pv-backup`：每日打包 DB+媒体目录 → openssl AES-256-CBC → curl PUT 到 `http://127.0.0.1:5244/dav`（OpenList，挂载移动云盘 `/home/备份/私人手记`），云端保留 KEEP_COUNT=1 |

关键约束：**服务器端所有媒体 I/O 都假设本地 POSIX 语义**——`os.OpenFile(O_EXCL)` 原子建文件、`os.Stat` 取 ModTime 生成 ETag、视频 `ReadAt` 随机读、`MkdirAll`、`safeFilePath` 路径穿越防护。这直接决定了下面的方案取舍。

## 二、三种方案对比

### 方案 A：文件系统级挂载（不推荐 ❌）

用 `rclone mount`（FUSE）或 `davfs2` 把 `http://127.0.0.1:5244/dav/…` 挂成本地目录，把 `storage_dir` 直接指过去。

不推荐的原因：

1. **破坏 POSIX 语义**：O_EXCL 原子性、rename 原子替换、ModTime、随机读在 WebDAV 挂载上都不保证。视频的 Range 播放（`videoReader` 逐块 `ReadAt`）会退化成大量网络往返，移动云盘速度下基本不可用。
2. **缓存自欺**：rclone VFS / davfs2 必须用本地磁盘做缓存才能保证性能——磁盘占用并没有省下来，还引入缓存不一致风险（OpenList 的云盘目录列表也有"已上传但列表不显示"的缓存问题）。
3. **启动迁移会被放大**：`migratePlainMedia` 启动时全目录扫描 + 读文件，挂载后变成全量网络 I/O，服务启动时间不可控。
4. **单点耦合**：OpenList 或移动云盘掉线（Cookie 过期是家常便饭，见第四节），整个手记功能读写全挂。
5. OpenList 的 WebDAV PUT 会先落到自身 `temp_dir` 再发起网盘上传，服务器临时磁盘照样占一份，"省磁盘"目的落空。

**结论：技术上能跑，生产上不能用。只适合一次性把存量文件搬到云端的搬运工具。**

### 方案 B：应用层异步双写（推荐起步 ✅）

本地仍是主存储与唯一读取源，上传成功后**入队异步 PUT 到 OpenList**，云端成为准实时二级副本。

- **架构**：新增 `webdav.go`（Go 标准库即可实现 PUT/GET/DELETE/MKCOL/PROPFIND，符合项目"不引重量级依赖"的惯例，约 200 行）+ 一个内存上传队列（单 worker 串行 + 失败退避重试，避免触发移动云盘限流）。
- **上传路径**：`addImage` 本地落盘 + DB 落库成功后，把 rel 路径投入队列；worker 读密文原样 PUT（**上传的是 AES-GCM 密文，云盘上永远只有密文**）。缩略图、语音、卡片 PNG 同理可选纳入。
- **读取路径**：完全不变（走本地），列表体验零影响。
- **删除/重传**：deleteImage 时同步 DELETE 云端对象（失败仅记日志，云端孤儿文件由对账任务清理）。
- **对账**：启动或每日低峰用 PROPFIND 列云端目录，把本地有、云端无的文件补传（幂等）。
- **配置**：`private_notes.json` 增加（该文件已有密码类敏感字段的存放先例，注意注释"禁止保存密码 Hash"的边界——WebDAV 口令属于运行凭据，与备份脚本中 DAV_PASS 同级）：

```json
{
  "cloud_sync": {
    "enabled": true,
    "dav_url": "http://127.0.0.1:5244/dav",
    "dav_user": "admin",
    "dav_pass": "…",
    "remote_dir": "/home/备份/手记图片",
    "scope": ["images", "thumbs"]
  }
}
```

- **收益**：图片副本从"每日一备"变成"秒~分钟级"，且与 `pv-backup.sh` 互为补充（一个是灾备包，一个是逐文件镜像）。
- **局限**：不省服务器磁盘（本地仍保留全量）。
- **工作量**：约 1 天（客户端 + 队列 + 配置 + 对账 + 单测），不动任何现有读取代码，风险低。

### 方案 C：云端为主 + 本地 LRU 缓存（真·省磁盘，谨慎 ✅⚠️）

原图以云端为主副本，本地只保留缩略图全量 + 原图 LRU 缓存；`/file` 未命中缓存时从 WebDAV GET → 解密 → 回缓存。

- 必须**把所有本地文件 I/O 收敛到一个 storage 接口**（put/get/delete/stat）之下：`addImage`、`ensureImageThumb`、`deleteImage`、`servePrivateMediaFile`、`readPrivateMedia`（导出）、`openVideoReader`（视频）、`migratePlainMedia`、卡片——共 8 处调用点要重构。
- 缩略图必须强制本地（480px 30~80KB，列表页一次几十张，走移动云盘会把列表拖死）。
- **视频强烈建议排除在此模式外**：200MB 分块加密 + Range 随机读，走移动云盘不可行；要么视频仍本地全量，要么接受"播放前整段拉取"的降级。
- 风险最大项是移动云盘的服务质量（见第四节），需要完整的降级链：云端 GET 失败 → 回本地缓存 → 仍无则 404 + 审计记录。
- 工作量约 3~5 天，且上线后可观测性（命中率、云端错误率）必须跟上。

## 三、安全性评估（结论：不降低现有安全水位）

1. **密文上云**：现有管线先加密后落盘，方案 B/C 上传的均为 AES-GCM 密文，密钥（SERVER_STATUS_ENCRYPT_KEY）不出服务器。云盘账号即使泄露，攻击者拿到的也是密文 + 每日备份包同样是 AES-256-CBC 加密的，安全模型一致。
2. **传输**：OpenList 与应用同机（127.0.0.1），无明文跨网传输；若将来 OpenList 移到别的机器，必须换 HTTPS，否则 WebDAV Basic Auth 明文暴露。
3. **访问控制不变**：图片 URL 仍是双层认证 + 归属校验的应用内接口，云盘不产生任何可直链访问的公开 URL（移动云盘分享链接机制完全用不到）。
4. **文件名天然规避已知坑**：OpenList/AList 社区有"WebDAV 上传中文名失败"的历史问题，而手记媒体文件名是 `f_xxx.ext` 纯 ASCII（随机 ID），天然免疫；云端目录名含中文时沿用 `pv-backup.sh` 已验证的百分号编码方式即可。

## 四、移动云盘（139）侧的现实风险

来源为 OpenList/AList 官方文档与社区 Issue 的已知情况：

| 风险 | 说明 | 应对 |
|---|---|---|
| Cookie/令牌过期 | 移动云盘驱动凭据会失效，挂载"经常掉线"是社区高频吐槽 | 双写方案下读不受影响；对账任务发现连续失败时在管理页告警 |
| 限流/风控 | 高频小文件 API 调用易触发；免费用户单文件上限约 2GB（图片 ≤20MB 无忧） | 单 worker 串行 + 重试退避；不做并发洪峰 |
| 上传时延 | PUT 是同步等网盘接口返回，单张 5~20MB 可能数秒~数十秒 | 异步队列天然消化，不影响用户上传体验 |
| 缓存不一致 | "文件已上传但列表不显示" | 对账以 PROPFIND 结果为准，不依赖列表实时性 |
| temp_dir 占盘 | OpenList WebDAV PUT 先落临时目录 | 双写方案中这由 OpenList 侧承担，量级=单张图片，可接受 |

**方案 C 的最大不可控项就是这张表**——移动云盘不是对象存储，无 SLA。因此建议把 C 定位成"扩容选项"而非"高可用选项"，且永远保留 `pv-backup.sh` 全量备份作为最后防线。

## 五、建议与路线

1. **如果诉求 = 防丢**：什么都不用改。现有 cron 备份已在移动云盘上。可选优化：KEEP_COUNT 从 1 调到 3~7，误删后有回滚窗口。
2. **如果诉求 = 准实时副本（推荐先做这个）**：实施方案 B（应用层异步双写），1 天工作量，零读取路径风险。
3. **如果诉求 = 省服务器磁盘**：在 B 稳定运行、云端对账连续无失败一段时间后，再评估方案 C，并把视频与语音明确排除或单独降级设计。

## 六、读路径专题：能否"先请求云盘上的资源"？

可以，而且实现成本比预想低——**读取代码已经天然收敛**：

| 读取场景 | 漏斗函数 | 说明 |
|---|---|---|
| 原图 / 缩略图 / 语音 / 视频封面 / 卡片 PNG | `servePrivateMediaFile`（private_store.go:253） | 全部 HTTP 媒体响应都经过这一个函数 |
| 导出 zip 内的图片 / 语音 / 封面 | `readPrivateMedia`（private_export.go:47） | 导出唯一入口 |
| 视频本体（Range 播放） | `openVideoReader`（private_store.go:392） | 分块随机读，**建议排除在云端读取外** |

只需在这两个漏斗里加"本地未命中 → WebDAV GET（拿到的仍是密文）→ 解密 → 响应 → 可选回写本地缓存"，即覆盖除视频本体外全部场景；`generateImageThumb` 读原图处加同样兜底（仅覆盖历史无缩略图的少量图片）。

### 推荐语义：本地缓存优先、云端兜底，而不是字面意义的"每次先打云端"

1. **每次请求都必打云端没有任何收益，只增加延迟**：本地与云端是同一份密文，不存在"云端更新"的问题。正确语义是 miss-driven——本地没有才去云端拿。
2. **省磁盘的正确开关是"上传成功后删除本地原图"**（配置项 `delete_local_after_upload`）。删除后"本地缺失"成为常态，读取自然变成"云端为主"，与上面的漏斗代码完全同一套。
3. **浏览器 immutable 缓存是关键盟友**：现有响应带 `Cache-Control: immutable` + ETag，每张图片每个浏览器基本只回源一次，云端的延迟代价只落在首次查看。
4. **分层策略**：
   - 缩略图：**永远本地**（列表页一次几十张，走移动云盘会把列表拖死；缩略图本来就小，省不了多少盘）
   - 原图 / 语音 / 视频封面：本地缓存优先 → 云端 GET → 回写缓存
   - 视频本体：仍留本地（200MB 分块随机读走云盘不可行）
5. **降级与熔断**：OpenList 移动云盘驱动 Cookie 过期是常态。云端 GET 设短超时（如 5s），连续失败 N 次进入冷却期（如 10 分钟）内直接按本地处理并告警。若已开 `delete_local_after_upload` 且云端不可用：原图暂时打不开（缩略图、正文、列表不受影响）——这是省磁盘模式的固有代价，需要接受。
6. **ETag 调整**：本地无文件时无法 os.Stat 取 ModTime，改用 `imageID + DB created_at` 生成，语义不变。

### 工作量

在方案 B（约 1 天）之上增加约 0.5~1 天：两个漏斗的云端兜底 + 缓存回写 + 熔断 + 配置项 + ETag 调整 + 测试。

## 七、带宽专题：目标是省服务器带宽时的唯一有效架构

**先澄清一个概念**：解密不费带宽——它是服务器内存里的 CPU 操作（毫秒级），与带宽无关。决定带宽的是**图片字节从哪条网络路径流出去**。

### 7.1 前面所有方案都不省带宽

方案 B（双写）与方案 C（云端读取）：浏览器仍从本服务器下载图片字节，出向带宽一分不减。方案 C 的"服务器从云端拉取再转发"只是把字节的来路换成了移动云盘（入向流量，一般不计费），出向不变。

### 7.2 唯一能省出向带宽的架构：浏览器直连移动云盘 CDN

服务器只响应一个 302 跳转（几百字节），图片字节从移动云盘 CDN 直达浏览器，完全不过服务器。查证结论：

- **139 驱动支持 302 重定向直链**，社区有"流量不经过服务器"的实测案例（NAS/strm 播放场景）；
- 但**加密内容无法走 302**：OpenList 的 crypt 驱动及一切"服务端处理数据流"的场景只能本地代理（AList Issue #4934），代理 = 流量回服务器 = 省不了。

而我们的图片恰恰是 AES-GCM 密文——这就是死结：**云上是密文，浏览器 `<img>` 标签没有解密能力**。解开这个结只有两条路：

### 7.3 路 A：客户端解密 + 302 直链（保安全，改动大）

- 服务器在私人空间解锁会话内把**每用户媒体密钥**下发给浏览器（现为全局密钥，不能直接下发，需引入"每用户媒体密钥"字段 + 存量图片服务端重加密迁移——只耗 CPU 不耗带宽）；
- 前端把手记图片的 `<img>` 改为"fetch 密文（302 直连移动云盘）→ WebCrypto AES-GCM 解密 → blob URL 渲染"，手记页、全屏查看器、卡片/语音分享页都要改；
- 上传改为"客户端不加密、服务器加密后上传"（现状不变）或保持现链路；
- **安全模型不变**：云盘上仍是密文，账号泄露拿不到照片；服务器出向带宽 ≈ 0（只有 302 与密钥下发这类小响应）；
- 视频可后续用同样思路分块解密，或视频暂不出带宽优化；
- 估计 3~5 天（后端密钥体系 + 前端解密渲染组件 + 迁移 + 测试）。

### 7.4 路 B：明文直链（改动小，安全降级，需拍板）

- 新图片**不加密**上传移动云盘，前端 `<img src>` 直接指向 OpenList 生成的临时直链；
- 最快见效（约 1~2 天），带宽同样基本归零；
- **代价**：移动云盘账号一旦泄露/Token 被取，照片明文裸奔；OpenList 必须公网可达（现为 127.0.0.1），需 HTTPS + 强认证 + 直链签名，暴露面变大；
- 全量备份包仍保持加密，但逐张原图已是明文。

### 7.5 配套前提与提醒

- 无论 A/B，**OpenList 必须从仅 127.0.0.1 监听改为公网可达**（HTTPS + 认证；A 方案下 OpenList 只吐 302 与密文，暴露风险相对可控），这是新增的攻击面，要单独评估。
- 139 的 302 直链存在时效/IP 绑定的可能性，需先实测"浏览器拿 302 后能否直接下载"再定案。
- **带宽大头其实是视频**：一次播放最多 200MB，远超全部缩略图+原图的一次性流量（缩略图 30~80KB/张、immutable 缓存后不重复消耗）。若带宽告急，图片优化完成后应把视频纳入同一架构。
